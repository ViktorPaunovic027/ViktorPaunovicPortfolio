Shared definitions

One definition per metric

GGR and NGR are dbt macros. Every model that reports them calls the same macro, so a definition changes in one place.

MetricDefinitionDated by
GGRReal-money stakes minus real-money winnings. Bonus-funded play is left out.Casino: session start. Sportsbook: settlement.
Bonus costBonus money that converted to withdrawable cash. Bonuses that are lost or expire cost nothing.The day the bonus converts
NGRGGR minus bonus cost.As GGR and bonus cost
Expected GGRWhat the house edge predicts: stake x (1 − RTP) for casino, stake x the bet's margin for sportsbook.As GGR
FTDA player's first successful deposit, counted once per player.The day of the deposit
DepositsSuccessful deposits only. Failed attempts and duplicate PSP callbacks are excluded.The day of the request
Active playerPlaced at least one real-money bet. Counted once per player in any period.Casino: session start. Sportsbook: placement.

The macros

Models never write stake - win themselves. They call the macro, and the dashboards show the wording from one reference table.

-- macros/metrics.sql
{% macro ggr(cash_stake, cash_win) -%}
    ({{ cash_stake }} - {{ cash_win }})
{%- endmacro %}

{% macro ngr(ggr, bonus_cost) -%}
    ({{ ggr }} - {{ bonus_cost }})
{%- endmacro %}

-- marts/metrics/kpi_daily_revenue.sql
{{ ngr('ggr_eur', 'bonus_cost_eur') }} as ngr_eur

What NGR leaves out

Operators define NGR differently. Many also deduct gaming duty and payment fees. This project deducts bonus cost only, and says so wherever NGR appears, so nobody compares it with a figure that means something else.

Why bonus play is outside GGR

Bonus money that a player loses never cost the operator anything. Counting its stakes would inflate GGR, and then counting the bonus again in NGR would double-count it. So bonus stakes and wins are kept in their own columns, and the cost enters NGR once, when the bonus converts to cash.

VIP history (SCD Type 2)

Revenue stays with the tier it was earned in

The CRM logs every tier change. The mart turns the log into date ranges, so each bet joins the tier the player held on that day.

Data quality

86 tests, run on every build

dbt runs the tests after each model it builds. If one fails, nothing downstream of it is built.

19Unique keys

The custom checks

  • GGR in the mart matches GGR computed straight from the source tables, so no join duplicated or dropped rows.
  • The KPI tables add up to the facts they summarise.
  • NGR equals GGR minus bonus cost on every row.
  • Every amount finds an exchange rate for its currency and day.
  • Each player's VIP versions follow each other with no gap or overlap.
  • Each player has exactly one current VIP version.
  • Each player has at most one FTD, and it is a successful deposit.
  • No player is active, or deposits, before the day they registered.

Problems in the source data

The simulator writes data the way real platforms do, problems included. The staging models fix them.

1,746PSP callbacks delivered twice. The first delivery is kept.
120,997Payment statuses sent in capitals by one PSP. Normalised.
780Currency-days with no published rate. The last rate is carried forward.
508VIP log rows that change nothing. They don't open a version.
7,076Bets still open at the end. Left out of GGR until they settle.

The tests caught a bug in my simulator. On a player's first day, play could be timestamped before they registered. For a Canadian player who registered late in the evening, that put their first bets on an earlier Malta day than their registration. The activity check failed, and I fixed the simulator.

Portability

Runs on a laptop, written to move

DuckDB builds and tests the whole mart locally. The SQL is kept easy to move to BigQuery.

Engine differences in four macros

Time-zone conversion, the date series, day of week and the float type differ between DuckDB and BigQuery. Each lives in one macro with a version per engine, and dbt picks the right one. Everything else uses SQL both engines accept. The BigQuery versions have not been run yet.

{% macro default__date_in_tz(ts, tz) -%}
    cast(timezone({{ tz }}, timezone('UTC', {{ ts }})) as date)
{%- endmacro %}

{% macro bigquery__date_in_tz(ts, tz) -%}
    date({{ ts }}, {{ tz }})
{%- endmacro %}

Rebuild it yourself

One command simulates the platform, builds the 41 models and runs the tests, in under a minute on a laptop.

# Python 3.12
pip install -r requirements.txt
python run_pipeline.py

The simulator uses a fixed seed, so every run produces the same data and the same numbers as this page.
